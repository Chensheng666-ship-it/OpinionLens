# 发布与自动更新（版本号怎么「自动更新」）

> 结论先放前面：**版本号不需要「运行时自动改」，它靠发版流程推进**。应用内「检查更新」比的是
> `app/desktop/package.json` 的 `version` 与 GitHub Release 的 **tag**；所以「让用户看到有新版本」= 改一次版本号 + 打 tag + 发 Release。
> 本仓库把「改版本号」这步做成了一个脚本，一次改全所有位置。

---

## 1. 版本号只有一个来源

| 位置 | 作用 | 由谁写 |
|---|---|---|
| `app/desktop/package.json` → `version` | **唯一来源**。Electron `app.getVersion()` 读它 | `scripts/bump_version.ps1` |
| `app/sidecar/version.py` → `FALLBACK_VERSION` | sidecar 直跑（没注入 `FS_APP_VERSION`）时的回退 | 同上 |
| `app/desktop/package-lock.json` | lock 顶部两处 version，跟着走 | 同上 |
| `README.md` 徽章 `release-x.y.z` | 展示用 | 同上 |
| `CHANGELOG.md` | 变更记录 | 同上（插入空小节，人工补内容） |

链路：`main.js` 启动 sidecar 时把 `FS_APP_VERSION=app.getVersion()` 注入环境 → `sidecar/version.py` 优先读它 →
`engine_runner.SIDECAR_VERSION`、`report_data.APP_VERSION`、`/api/system` 回报的版本全部同源 →
界面「关于」页显示的版本 = `package.json`。**离线自测里有断言**：`FALLBACK_VERSION` 必须等于 `package.json` 的 version，
两处不同步就会红（这正是过去出现「界面 0.6.0 / 包 0.2.2 / 报告 0.3.0」三处不一致的根因）。

## 2. 发一个版本（推荐顺序）

```powershell
cd <仓库根>

# 0) 改完代码，先自测
.\app\scripts\selftest.ps1

# 1) 升版本号（同步 package.json / package-lock / version.py / README 徽章 / CHANGELOG 空小节）
.\scripts\bump_version.ps1 -Version 0.4.1 -Summary "设置页新增软件更新与数据目录迁移"

# 2) 补 CHANGELOG 正文（脚本只插骨架）

# 3) 再跑一次自测（会校验版本号一致性），然后提交
.\app\scripts\selftest.ps1
git add -A; git commit -m "release: 0.4.1"
git tag v0.4.1; git push; git push --tags

# 4) 出安装包（内置便携 Python/MediaCrawler，用户装完即用）
.\app\scripts\build_installer.ps1 -SkipResources

# 5) 签名（私钥在仓库外；version 与 tag 一致），生成 OpinionLens-Setup-0.4.1.exe.sig
node app\scripts\sign_update.js sign --key D:\keys\opinionlens-update.pem --version 0.4.1 `
  build\installer\output\OpinionLens-Setup-0.4.1.exe

# 6) 发 GitHub Release（tag = v0.4.1，资产挂 OpinionLens-Setup-0.4.1.exe 与 OpinionLens-Setup-0.4.1.exe.sig）
```

> 发布密钥只生成一次：`node app\scripts\sign_update.js keygen --out D:\keys\opinionlens-update.pem`，
> 把输出的公钥加进 `app/desktop/update.js` 的 `UPDATE_SIGNING_PUBLIC_KEYS` 后再出包。私钥离线保存，不进仓库、不挂到 Release。
> 没有 `.sig` 或公钥未固定的版本，应用内「下载并安装」会拒绝，用户只能「打开发布页」手动下载。

> GitHub Release 的 **tag 名必须是 `v<version>`**（`v0.4.1`）。应用内检查更新会 `replace(/^v/i,'')` 后与本地版本比较，
> tag 写成 `0.4.1` 也能识别，但统一加 `v` 更稳。

## 3. 应用内「检查更新」是怎么工作的

「设置 → 关于 → 软件更新 → 检查更新」：

1. 主进程 `app:checkUpdate` 请求 `https://api.github.com/repos/<repo>/releases/latest`（repo 可用环境变量 `FS_UPDATE_REPO` 覆盖）；
2. 用 `app/desktop/update.js` 的 `compareVersions()` 与 `app.getVersion()` 比较（数值比较，`1.0.0 > 1.0.0-beta.1`）；
3. `hasUpdate=true` 时展示版本对比 + Release 正文（截断 4000 字），并给两个出口：
   - **打开发布页**：`shell.openExternal(releaseUrl)`，用户自己去 GitHub 下载；
   - **下载并安装**：`app:downloadUpdate` 只下载本次检查选中的安装包；先用固定的发布者公钥验 `<安装包>.sig`
     （绑定名称/版本/大小/SHA-256），再流式下载到 `%TEMP%\OpinionLens-update\dl-XXXX\`（进度条 + 百分比），
     摘要对上才保留；「运行安装包」启动前再按记录的摘要复核，通过后 `shell.openPath` 启动，装完覆盖旧版本，数据目录不变。
     每一跳重定向都必须仍在 GitHub 下载域名内。
4. GitHub 匿名 API 有 **60 次/小时** 限流。超限或断网时自动退化为解析
   `https://github.com/<repo>/releases/latest` 的 302 跳转拿到 tag（`source:'redirect'`）——能判断「有没有新版」，
   但拿不到资产列表，此时只能「打开发布页」手动下载。

### 为什么不做成 Electron 静默自动更新（electron-updater）

`electron-updater` 需要在安装包里签好名并提供 `latest.yml`，未签名构建在 Windows 上会被 SmartScreen 拦在更新环节；
本项目当前**不做 Authenticode 代码签名**（个人项目成本考虑）。所以这里用「检查 + 手动确认下载 + 启动安装包」的方案：
不依赖证书，改用自管的 Ed25519 发布密钥给安装包摘要签名（见上文第 2 节第 5 步）、用户全程知情、失败可回退。后续若拿到证书，再切 `electron-updater` 也不冲突（版本号来源相同）。

## 4. 数据目录可搬家（默认路径不再是唯一选择）

「设置 → 关于 → 数据存储 → 更改数据目录…」：

1. 选一个新目录（建议非系统盘）；
2. 确认后主进程：停 sidecar → 复制数据（跳过 `electron/` Chromium 缓存与兼容标记）→ 写配置 → 自动重启应用；
3. **旧目录保留不删**（确认新目录能正常跑之后再手动清理）；
4. 配置写在固定位置 `%APPDATA%\OpinionLens\user-config.json` 的 `dataDir` 字段——不跟数据目录走，
   否则换盘后就找不到自己的配置了；「恢复默认目录」删掉该字段并重启。

迁移会被拒绝的情况：目标与当前目录相同/互为上下级、目标已存在 `app.db`（`DATA_TARGET_OCCUPIED`）、目标不可写（`DATA_TARGET_NOT_WRITABLE`）。

## 5. 常见问题

| 问题 | 处理 |
|---|---|
| 「检查更新」报 `GitHub API 不可用` | 匿名限流（60/h）。等一会儿再试，或直接看 `source:'redirect'` 的版本号并「打开发布页」 |
| 下载到一半失败 | 主进程只允许 GitHub https 域名；公司代理/杀软拦截会报「下载内容不是有效安装包」；重试即可，临时文件会清理 |
| 装完版本没变 | 确认 Release 的 tag 与 `package.json` 一致，且下载的是 `OpinionLens-Setup-<ver>.exe`（不是 zip / blockmap） |
| 数据目录改了但数据没过去 | 迁移失败会回滚并保留原目录，看 `%APPDATA%\OpinionLens\logs\main.log` 里的 `数据目录迁移失败` 行 |
